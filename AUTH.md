# Авторизация веб-приложения

Frontend использует существующий backend без изменений его API:

- `POST /auth/login`: `username`, `password`, `deviceId`, `deviceName`.
- `POST /auth/refresh`: `refreshToken`, сведения об устройстве.
- `POST /auth/logout`: `refreshToken`.
- Для защищённых запросов — `Authorization: Bearer <accessToken>`.

Все URL берутся из `VITE_API_URL`, `VITE_REPORTS_URL`, `VITE_SOCKET_URL` в `.env` при сборке Vite. Refresh-токен отправляется только на API, не на сервис отчётов и не в WebSocket.

## Сохранение сессии

Пара токенов хранится одной JSON-записью `dreamhouse.auth.session.v1` в localStorage. Это сохраняет вход после перезагрузки браузера и позволяет вкладкам одного origin использовать актуальную пару. Старый ключ `token` читается для переходного периода: действующий старый access работает до истечения, затем требуется новый вход для получения refresh.

У текущего backend нет HttpOnly-cookie. localStorage доступен JavaScript и не защищает токены от XSS. Не вставляйте токены в логи, отчёты об ошибках или переписку.

## Вкладки и обновление

Все операции login, refresh и logout согласуются через Web Locks. Нужен современный браузер и HTTPS; локально подходят `http://localhost` и `http://127.0.0.1`. При отсутствии Web Locks вход сообщает об этом до отправки пароля. Разные origin (например, localhost и 127.0.0.1) имеют отдельные сессии.

Перед запросом почти истёкший access обновляется; после `401` запрос повторяется максимум один раз. Запоздавший `401` использует уже обновлённый токен. `403` не запускает refresh. Отозванная сессия не отправляет свой refresh повторно: backend мог бы завершить остальные сессии пользователя.

Перед refresh сохраняется отметка незавершённого обновления. При потере ответа или закрытии вкладки в этот момент старый refresh не используется повторно: нужен новый вход. На `429` сохраняется сессия и выдерживается `Retry-After`. Обычная сетевая ошибка бизнес-запроса сама по себе не удаляет токены и не повторяет изменение данных.

Выход немедленно очищает локальную сессию во всех вкладках и пытается отозвать её на сервере. Если выход совпал с refresh, его поздний результат не восстанавливает вход, а новая пара отзывается. Без сети серверный отзыв не гарантируется.

WebSocket переподключается с новым access. Смена пароля завершает текущую сессию: после успешного изменения войдите с новым паролем. Стили и разметка существующих форм не менялись.

## Проверка

```powershell
node tests/auth-client.test.cjs
npm run build
```

Автоматические проверки используют синтетические токены и подменённые ответы: реальные backend, учётные записи и БД не затрагиваются.

После пересборки контейнера проверьте вход, обновление страницы, две вкладки, выход в одной вкладке, отчёты, загрузку файлов, уведомления и обязательную смену пароля на тестовой учётной записи.

## Уточнения хранения и восстановления

Access и refresh не попадают в состояние Redux или результат входа. Redux DevTools отключён, поскольку аргументы действий входа и смены пароля содержат пароли. WebSocket подписан непосредственно на изменения сессии.

При отсутствии access в сохранённой сессии с корректным refresh, идентификатором пользователя и поколением входа сначала восстанавливается пара токенов, затем запрашивается профиль. Некорректный срок access проверяется по JWT; если определить его нельзя, выполняется refresh.

После ошибки 500 на refresh повтор не выполняется: текущий сервер не гарантирует, что ротация не была зафиксирована до ошибки. Потребуется новый вход. Это ограничение контракта бэкенда, а не ошибка обычного запроса данных.
